# v1.3 센서·장치 제어 설계 노트

v1.3.0 마일스톤에서 PC 장치를 다루는 기능들의 설계 메모다. 기능마다 절 하나씩.

## 오디오 장치 칸 (#145 → #159, 드라이버 #160)

**목표.** SmartThings 루틴이 "지금 출력이 헤드셋(2번 칸)이면" 같은 조건을 쓰게 한다. 장치를 **바꾸지는 않는다** — #145의 원격 전환(`audio_output`/`audio_input`, 텔레그램 `/output`·`/input`, 비공개 `IPolicyConfig`)은 v1.3.0에서 뺐다(#159).

**칸 방식.** SmartThings의 목록은 enum이 고정이라 장치 목록을 그대로 내보낼 수 없다. 설정 `audio.outputs`·`audio.inputs`가 각각 칸 1–5의 **장치 이름** 목록이다(순서 = 칸 번호).
이름으로 저장하는 이유: 엔드포인트 id(`{0.0.0.00000000}.{guid}`)는 드라이버 재설치·USB 포트 변경 때 바뀐다. 매칭은 앞뒤 공백·대소문자를 무시한 이름 일치.

**자동 배정(#159).** 사용자가 칸을 채우지 않는다. 서비스가 활성 장치 목록을 받을 때마다 칸이 없는 장치에 **가장 낮은 빈 칸**(중간의 빈 칸 먼저, 그다음 끝)을 주고 `config.json`에 이름으로 저장한다(`config.AssignAudioSlots`, `service/audio_devices.go`). 기본 장치가 먼저라 빈 상태에서는 쓰고 있는 장치가 1번 칸이 된다. 다섯 칸이 차면 더 받지 않는다. 사라진 장치는 칸을 지키고 `present:false`로 보인다.
- `media.enabled`가 꺼져 있으면 배정하지 않는다(칸은 audio 블록의 일부이고, 목록도 오지 않는다).
- POST `/api/config`는 칸을 **바꾸지 못한다**(`config.Normalize`가 늘 현재 값을 쓴다). 앱이 예전에 읽은 목록을 보내도 그 사이의 배정이 지워지지 않게.
- 비우는 길은 앱 기능 탭의 [초기화] 하나다: `POST /api/audio/slots/reset`이 두 목록을 비우고 지금 연결된 장치로 다시 채운 뒤 저장한 칸을 돌려주고 `audio.changed`를 민다. 목록을 아직 못 받았으면 빈 채로 두고, 다음 목록이 채운다.
- 앱은 읽기 전용 목록(칸 N · 이름 · "(연결 안 됨)")과 [새로 고침] · [초기화]만 보인다. "(연결 안 됨)"은 앱이 같은 세션에서 직접 읽은 목록으로 판단한다.

**user-action.** 목록은 `IMMDeviceEnumerator::EnumAudioEndpoints(eRender|eCapture, DEVICE_STATE_ACTIVE)`의 `{name(PKEY_Device_FriendlyName), default}`이다. id는 기본 장치를 가리는 데만 쓰고 프로세스 밖으로 내보내지 않는다. 별도 동사는 없고 `audio get` 응답에 `outputs`·`inputs`로 붙는다(best effort). 트레이 앱은 같은 함수를 프로세스 안에서 불러 30초 하트비트의 `audio_devices`로 보낸다.

**status.** 기존 `audio` 블록에 `outputs`·`inputs: [{slot, name, present, default}]`(채운 칸만, 없으면 빈 배열). 기본 출력은 트레이가 3초마다 보내는 audio 샘플의 `device`로 판단해 Windows에서 직접 바꿔도 기존 `audio.changed` 푸시로 바로 반영된다. 목록·기본 입력·칸이 바뀌면 `audio.changed`를 민다. features는 칸이 있으면 `audio_output`/`audio_input` — 이제 "칸을 보고한다"는 뜻이고 명령은 없다.

**버린 대안.** 장치 id 저장(위 이유), 사용자가 칸을 고르는 편집기(#145 — 루틴에 쓸 번호만 있으면 되고, 편집기는 앱이 읽은 오래된 목록으로 서비스의 배정을 덮어쓸 수 있었다), 서비스가 상태 조회마다 목록 읽기(세션 프로세스 생성 비용 — 하트비트와 기존 배경 읽기에 얹었다), 새 푸시 타입(드라이버가 이미 `audio.changed`의 status 전체를 적용한다).

**실기 확인 필요.** Bluetooth 헤드셋의 끊김·재연결 때 `present`와 배정 순서, 같은 이름의 장치가 둘일 때(한 칸만 차지한다).

## 스피커·마이크 상태 (#159, 드라이버 #160)

**목표.** 루틴 조건으로 쓸 소리 상태: 스피커에서 지금 소리가 나는지, 스피커 음소거, 현재 출력 장치, 마이크 음소거, 현재 입력 장치. 마이크를 쓰는 앱이 있는지는 기존 `privacy`(#143)가 맡는다. 바꾸는 명령은 더하지 않는다(볼륨 · 음소거 · 미디어 키는 v1.2 그대로).

**계약.** `status.audio`에 세 키를 더한다. 셋 다 **늘 있고**, 모르면 `null`이다(`available:false`일 때도 `null`).

```json
"audio": { "available": true, "volume": 35, "muted": false, "device": "스피커 (Realtek(R) Audio)",
           "playing": true, "input_device": "마이크 (Realtek(R) Audio)", "input_muted": false,
           "updated_at": "…", "outputs": […], "inputs": […] }
```

- `playing`(bool|null): 기본 출력에서 지금 소리가 나는지.
- `input_device`(string|null) · `input_muted`(bool|null): 기본 입력 장치(eCapture/eConsole)의 이름과 `IAudioEndpointVolume::GetMute`. 입력 장치가 없거나 못 읽으면 둘 다 `null`.
- 푸시 `audio.changed`는 볼륨 · 음소거 · 출력 장치 · **입력 장치 · 입력 음소거 · playing**이 바뀔 때 나간다. `data`에 `input_device` · `input_muted` · `playing`이 문자열로 더해지고(아는 것만, 모르면 키가 없다), 드라이버는 늘 그렇듯 함께 온 status 전체를 적용한다.
- playing**만** 바뀐 푸시는 앞 `audio.changed`와 최소 2초(`playingPushGap`) 간격을 둔다. 그 안의 변화는 간격이 끝날 때 그때의 상태로 한 번 나가고, 그사이 볼륨 등으로 푸시가 나가면 그것이 대신한다(`pushSpacer`, `service/audio_state.go`).

**입력 장치 — 어디서 읽나.** 기존 볼륨 · 음소거와 똑같다. `useraction.ReadAudio`(트레이의 3초 변화 확인 · 30초 하트비트, 트레이가 없으면 서비스의 배경 `user-action audio get`)와 모든 `audio` 동사의 응답이 같은 열기(`openEndpoint(eCapture)`)로 입력 장치를 함께 읽어 오디오 샘플의 `input`(`{present, device, muted}`)에 담는다. 명령 응답도 늘 담으므로 응답 하나가 입력 상태를 지웠다 되살리는 일이 없다. 입력 쪽 실패는 출력 읽기를 망치지 않는다(best effort).

**playing — 어디서 읽나 (결정).** `IAudioMeterInformation::GetPeakValue`(기본 eRender/eConsole 엔드포인트, 볼륨과 같은 `Activate`, out 포인터는 `o.call(...)` 인자 안에서만 변환)를 **트레이 앱이 사용자 세션에서 300ms마다** 읽는다(`gui/playing.go`, `useraction/peak.go`).
- 피크는 엔진 한 주기(약 10ms)의 최댓값이라 한 번 읽어서는 음악의 조용한 구간과 정지를 가릴 수 없다. 서비스(세션 0)가 `user-action`을 250–500ms마다 띄우는 건 프로세스 생성 비용 때문에 안 되고, 세션 0에서 직접 미터를 읽는 것은 사용자의 기본 장치와 어긋날 수 있다. 볼륨 · 미디어 세션을 이미 트레이가 프로세스 안에서 읽어 보내는 구조에 그대로 얹었다.
- 판정: 피크 > 0.001(약 -60 dBFS)이면 곧바로 재생 중, 5초 연속 그 이하이면 재생 아님, 미터를 못 읽으면(출력 장치 없음 등) 모름. `media.enabled`가 꺼져 있으면(tray.json, 3초마다 확인) 읽지 않고 모름.
- 바뀌면 3초 변화 확인을 바로 돌려 audio 블록(`"playing": true|false`, 모르면 키 없음)을 보내고, 30초 하트비트가 매번 다시 보낸다. 서비스는 플래그를 오디오 샘플과 **따로** 둔다(`dev.playing`) — 명령 응답에는 playing이 없으므로 샘플에 넣으면 명령마다 "모름"이 된다. 마지막 하트비트에서 90초(`idleHeartbeatTTL`)가 지나면 `null`. 처음 받은 값은 기준값이라 푸시하지 않는다(오디오 샘플과 같음).
- 따라서 **트레이 앱이 대상 세션에서 돌고 있어야** playing이 나온다. 없으면(설치 직후, 다른 세션) `null`이다. 입력 장치 · 입력 음소거는 트레이 없이도 서비스의 배경 읽기로 나온다.
- 피크는 엔진이 섞은 스트림을 따르므로, 엔드포인트 음소거가 미터를 0으로 만드는지는 장치(하드웨어 볼륨이냐 아니냐)에 따라 다를 수 있다. 그래서 playing은 "소리가 나는 스트림이 있다"로 읽고, 음소거는 `muted`로 따로 본다.

**텔레그램 · WebUI.** `/status`의 출력 줄에 ` · 재생 중|소리 없음`, 입력 줄 `입력: 마이크 · 음소거|켜짐`(아는 것만). WebUI 원격 카드의 볼륨 줄 아래에 `스피커: 재생 중 · 마이크: 음소거`. 새 명령은 없다.

**실기 확인 필요.** 실제 장치에서 피크 값의 크기(무음 스트림의 잡음이 0.001을 넘지 않는지), 음소거 · 볼륨 0일 때 피크가 0이 되는지(장치마다), Bluetooth 헤드셋 · HDMI 출력에서 `GetPeakValue`가 값을 주는지, 기본 장치를 바꿀 때 300ms 읽기가 바로 따라가는지, 마이크 음소거를 Windows 설정 · 키보드 키로 바꿀 때 3초 안에 반영되는지.

## 카메라·마이크 사용 감지와 사용 중 종료 보호 (#143, 드라이버 #152)

### 감지

Windows는 앱이 카메라·마이크를 쓸 때마다 사용자별 동의 저장소에 시각을 남긴다.

```
HKCU\Software\Microsoft\Windows\CurrentVersion\CapabilityAccessManager\ConsentStore\
    {webcam,microphone}\<패키지 앱>                 LastUsedTimeStart / LastUsedTimeStop (FILETIME QWORD)
    {webcam,microphone}\NonPackaged\<exe 경로>
```

`LastUsedTimeStop == 0`이고 `LastUsedTimeStart != 0`인 항목이 하나라도 있으면 그 장치는 **사용 중**이다.

- 서비스(LocalSystem)는 HKCU가 자기 것이므로, 명령 대상 세션(`findUserSession`, 모든 명령이 따르는 그 세션)의 사용자 토큰에서 SID를 얻어 `HKU\<SID>\...`를 **읽기만** 한다.
- 하이브가 안 올라와 있거나(로그인한 사람 없음) 목록을 못 읽으면 `unknown`. 장치 키 자체가 없으면(한 번도 안 씀) `idle`.
- 3초마다 읽고(`privacyScanInterval`), 설정 저장 직후 한 번 더 읽는다. 두 장치 상태가 바뀔 때만 `privacy.changed`를 푸시한다. 옵션을 켜거나 끄는 것도 변화로 푸시한다.
- 키 이름(앱 정체)은 읽고 버린다. 상태·로그·알림 어디에도 앱 이름은 나가지 않는다.
- 코드: `service/privacy`(읽기·판정), `service/privacy_guard.go`(루프·보호), 설정 `internal/config/privacy.go`.

### 계약

설정(`config.json`):

```json
"privacy": { "enabled": false, "guard": "warn" }      // guard ∈ off | warn | block
```

`GET /st/v1/status` — `privacy.enabled`일 때만 키가 있다. `features[]`에 `"privacy"`.

```json
"privacy": { "camera": "in_use", "microphone": "idle", "since": "2026-10-01T20:45:00+09:00" }
```

- `camera`, `microphone`: `in_use` | `idle` | `unknown`
- `since`: 사용 중인 것이 있으면 그중 가장 이른 시작, 아니면 마지막 사용이 끝난 시각. 모르면 `""`.

푸시 `privacy.changed` — `data`는 status의 `privacy` 블록과 같은 JSON(`activity.changed`와 같은 방식). 옵션을 끄면 `data: null`이고 status에서 블록과 `features`의 `privacy`가 빠진다.

### 사용 중 종료 보호

대상: `shutdown` · `restart` · `suspend` · `hibernate`.

| 경로 | 보호 |
|---|---|
| SmartThings(`/st/v1/command`, 예전 `/{secret}/{command}` URL) | 예 |
| 텔레그램(확인 후 실행, `/now`, [바로 실행]) | 예 |
| WebUI(`/api/command` by=webui) | 예 |
| 예약(앱·WebUI·텔레그램·SmartThings 예약, 원격 유예 포함)이 실행되는 순간 | 예 |
| PC 앞 데스크톱 앱 · 트레이 · 토스트 버튼 | 아니오 |
| `forceshutdown` | 아니오(비상 탈출구) |

- `warn`(기본): 즉시 명령은 실행하고 알림(`remote.received` / `remote.grace_scheduled`)에 `in_use` 필드를 붙인다(텔레그램 문구 "⚠️ 카메라 사용 중", 유예 토스트에도 한 줄). 예약은 실행 시각에 사용 중이면 **한 번만** 유예 시간(`grace_seconds`)만큼 미루고 `privacy.extended` 알림을 보낸 뒤, 다음엔 실행한다.
- `block`: 실행하지 않는다. `/st/v1/command`와 WebUI는 `409 {"error":"device_in_use","devices":["camera"]}`, 예전 URL은 409 본문 한 줄, 텔레그램은 사유 문구로 답한다. 예약은 취소(`by: device_in_use`)하고 `privacy.blocked` 알림을 보낸다.
- 거절된 명령은 `last_command`에 기록하지 않는다.
- 판정 직전에 저장소를 한 번 더 읽어(최대 3초 늦은 값 대신) 판단한다.

### 실기 확인

- Windows 카메라 앱 · Teams/Zoom/Discord 통화를 켜고 끄며 3초 안에 `camera`/`microphone`이 바뀌는지(패키지 앱과 `NonPackaged` 둘 다).
- 잠금 상태 · RDP 세션 · 다른 사용자 전환에서 대상 사용자의 값이 나오는지, 로그아웃 시 `unknown`인지.
- 앱이 비정상 종료되면 `LastUsedTimeStop`이 0으로 남아 계속 사용 중으로 보일 수 있다(HASS.Agent 등에서 알려진 현상). 재현되면 프로세스 생존 확인 등 보정을 별도 이슈로.

## 스피커·마이크 상태 — 요약 (드라이버 #160)

전환 대신 **루틴 조건으로 쓸 상태**만 보낸다. 서비스 쪽(칸 자동 배정, 피크 미터, 푸시)은 #159, 드라이버 쪽은 [`edge-driver.md`](edge-driver.md) §4.3이다.

- **계약**: status·푸시의 `audio`에 `playing`(bool|null, 기본 출력에서 지금 소리가 나는지), `input_device`(string|null), `input_muted`(bool|null)이 더해진다. `outputs`·`inputs`(`{slot, name, present, default}`)는 그대로이고 칸은 PC 앱이 정한다. `monitors`, `features`의 `monitor`, 명령 `audio_output`·`audio_input`·`monitor_*`는 없다.
- **드라이버**: 컴포넌트 `sound`("소리", 프로필 v16)에 `pcSpeaker`(`summary` · `names` · `output` `none`/`1`–`5` · `playing` `playing`/`idle`/`unknown` · `muted`)와 `pcMic`(`summary` · `names` · `input` · `muted`). 명령은 없다. 화면에는 `summary`("3 헤드셋 · 재생 중", 앞의 번호가 기본 장치의 칸) 한 줄씩만 보인다. null이나 없는 값은 `unknown`이고(null 속성은 앱의 "상태 정보 미수신"을 부른다), PC가 꺼지면 `playing`만 `unknown`, 칸·음소거는 마지막 값이다.
- 카메라·마이크 **사용 중**은 위 `pcPrivacy`(#143, #152) 그대로다.
